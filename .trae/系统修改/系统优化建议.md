# 系统优化建议

> 2026-05-18 | 基于全面审查后的优化项

---

## 一、代码架构

### 1.1 缺少 Service 层（★★★★★）

**现状**：除 `AuthServiceImpl` 外，28 个 Controller 全部直接注入 Mapper，业务逻辑和控制器代码混在一起。

**问题**：重复代码多，比如多处都在循环里 `selectById`，改一处逻辑要改多处。Controller 里塞了几十行 SQL 拼接，不易维护。

**建议**：抽取核心业务 Service，比如 `RepairService`、`StudentService`、`UtilityService`。Controller 只负责接收请求和返回结果，Service 处理业务逻辑，Mapper 只做数据访问。

**涉及文件**：几乎所有 Controller。

---

### 1.2 残留的 N+1 查询（★★★★）

**现状**：`StudentController.list()` 已优化，但同文件第 479 行附近仍有：
```java
List<Bed> allBeds = bedMapper.selectList(null);  // 全表查所有床位
// 然后循环：
Room room = roomMapper.selectById(bed.getRoomId());      // N+1
Building building = buildingMapper.selectById(...);        // N+1
```

**建议**：参照已优化的 `list()` 方法，改成批量查询 + Map 关联。

**涉及文件**：`StudentController.java` 第 479 行附近，`MaintenancePersonController.java` 新版工单查询。

---

### 1.3 前端导出方案不统一（★★★）

**现状**：

| 端口 | 导出方式 | 原理 |
|------|---------|------|
| 管理员端（大部分） | 前端 XLSX.js | 只导当前表格内存数据 |
| 宿管端 | 后端 POI | 能导全量数据、支持筛选条件 |

学生管理导出（后端 POI）能按楼栋筛选导出，管理员端的导出（前端 XLSX.js）如果没有先加载全量数据，导出的只是当前页。

**建议**：统一用后端 POI 导出，支持筛选条件，数据量不受前端限制。

**涉及文件**：`admin/` 下使用 `XLSX.utils.json_to_sheet` 的 10+ 个页面。

---

## 二、安全

### 2.1 权限控制不够严格（★★★★）

**现状**：`SecurityConfig.java` 只配了 `.anyRequest().authenticated()`，没有角色级别的 URL 拦截。任何登录用户都能访问所有 URL。

**建议**：加 `@PreAuthorize` 注解或配置角色 URL 规则，比如管理员接口只能 userType=3 访问。同时保留数据层过滤作为双重保障。

**涉及文件**：`SecurityConfig.java`、各 Controller。

---

### 2.2 HTTP 明文传输（★★★）

**现状**：所有数据（包括登录密码）通过 HTTP 明文传输。论文里自己写了"存在高风险"。

**建议**：部署时启用 HTTPS（Let's Encrypt 免费证书），在 Spring Boot 里配置 SSL，Nginx 强制 HTTP 跳转 HTTPS。

---

## 三、功能完善

### 3.1 维修人员不能改密码（★★★）

**现状**：三种老角色（学生、宿管、管理员）都有修改密码功能，维修人员端没有。

**建议**：在 `maintenance/profile/` 加一个修改密码页面，后端加 `/api/maintenance/password` 接口。改动量很小。

**涉及文件**：新建 `maintenance/profile/index.vue`，`MaintenancePersonController.java` 加接口。

---

### 3.2 消息通知是被动轮询（★★★）

**现状**：学生收到消息需要手动刷新页面，报修完成了也不知道。

**建议**：用 WebSocket 实现实时推送。Spring Boot 自带 WebSocket 支持，前端用 `@vueuse/core` 的 `useWebSocket`。改动不大但体验提升显著。

---

### 3.3 没有移动端适配（★★★）

**现状**：只有 PC Web 端。学生打卡、缴费这些功能在手机上更实用。

**建议**：开发微信小程序版本，或者至少让现有 Web 端支持响应式布局。Element Plus 本身支持响应式，主要是调一下 layout。

---

### 3.4 维修人员端缺少退出确认（★★）

**现状**：维修人员点退出直接退，没有确认提示。其他角色也没有。

**建议**：加了 `ElMessageBox.confirm` 确认弹窗。三行代码的事。

---

## 四、数据

### 4.1 旧数据兼容（★★★）

**现状**：`repair` 表里 `repairPerson`（旧，存名字字符串）和 `maintenance_id`（新，存维修人员 ID）并存。旧报修记录在新体系下维修人员名字显示不出来。

**建议**：写一个 SQL 脚本，把旧 `repairPerson` 字段里的名字和 `maintenance_person` 表的 `name` 做匹配，匹配到就回填 `maintenance_id`。匹配不到的数据保持旧字段展示。

---

### 4.2 输入校验不够（★★）

**现状**：部分表单缺少前端/后端校验，比如密码可为空、报修描述不填也能提交、手机号格式不检查。

**建议**：前端表单一律加 `el-form` 的 `rules`，后端口加 `@NotBlank`、`@Pattern` 等校验注解。

---

## 五、按优先级排序

| 优先级 | 项目 | 改动量 | 影响范围 |
|--------|------|--------|---------|
| ★★★★★ | 加 Service 层 | 大 | 全系统 |
| ★★★★ | 修残留 N+1 查询 | 小 | 单文件 |
| ★★★★ | 权限控制加强 | 中 | 安全相关 |
| ★★★ | 导出方案统一 | 中 | 管理员端 10+ 页 |
| ★★★ | 维修人员改密码 | 极小 | 新增 1 页 + 1 接口 |
| ★★★ | 旧数据兼容 | 小 | 1 条 SQL |
| ★★★ | 消息实时推送 | 中 | 消息模块 |
| ★★★ | HTTPS | 极小 | 配置改动 |
| ★★★ | 移动端适配 | 大 | 全前端 |
| ★★ | 输入校验 | 中 | 多文件 |
| ★★ | 退出确认 | 极小 | 4 个 layout 文件 |

**建议优先做**：4.1 旧数据兼容 + 3.1 维修人员改密码（改动最小、立刻能用）+ 1.2 修残留 N+1 + 4.2 输入校验。
