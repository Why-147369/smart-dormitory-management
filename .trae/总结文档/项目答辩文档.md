## Q1：项目中用了什么加密方法？为什么选它？

我用的是 **BCrypt**，Spring Security 自带的密码加密器。

配置在 `dormitory-admin/src/main/java/com/dormitory/config/SecurityConfig.java`，里面定义了一个 Bean：

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

选 BCrypt 三个原因：一是单向哈希，不可逆，数据库泄露也还原不了明文；二是每次加密自动加随机盐值，两个用户设同样密码，密文也不同；三是慢哈希，默认 1024 轮运算，暴力破解成本很高。

具体使用的地方：
- 新增学生：`StudentController.java` 第 54 行附近，`passwordEncoder.encode("123456")`
- 新增宿管：`ManagerController.java`，同样调用 encode
- 登录验证：`AuthServiceImpl.java`，用 `passwordEncoder.matches(明文, 密文)` 比对

## Q2：BCrypt 的"盐值"是什么意思？

盐值就是一段随机字符串，加密前和明文密码混在一起再哈希。

举个例子：如果不用盐值，A 和 B 都设密码 123456，数据库里两条记录密文一模一样。黑客破解一个就全知道了。

用了盐值之后，BCrypt 每次自动生成不同盐值，同样的 123456 会产出完全不同的密文，比如：
- A：`$2a$10$XyZ...abc`
- B：`$2a$10$Def...xyz`

这就防住了彩虹表攻击，黑客没法预先算好一个密码字典来批量比对。

## Q3：项目是什么架构？

**B/S 架构**（浏览器/服务器），前后端分离。

前端是 Vue 3 项目，独立部署，开发端口 5173；后端是 Spring Boot，端口 8080。前端通过 HTTP 请求后端 RESTful API，JSON 格式交互。

后端内部是 **MVC 三层**：
- Controller 层：接收请求、参数校验，调 Service，返回结果
- Service 层：核心业务逻辑，比如登录认证在 `AuthServiceImpl.java`
- Mapper 层：数据库操作，用的是 MyBatis-Plus，大部分单表查询不用写 SQL

项目启动类：`dormitory-admin/src/main/java/com/dormitory/DormitoryApplication.java`

## Q5：JWT 认证是怎么实现的？

三个文件配合完成：

**①生成 Token — `JwtUtil.java`**（`dormitory-admin/src/main/java/com/dormitory/utils/JwtUtil.java`）
登录时调用 `generateToken(userId, userType)`，把用户 ID 和角色类型写进 Token 的 Payload，设 7 天过期（配置在 `application.yml` 的 `jwt.expiration: 604800000`）。

**②拦截验证 — `JwtAuthenticationFilter.java`**（`dormitory-admin/src/main/java/com/dormitory/config/JwtAuthenticationFilter.java`）
每个请求到达后端，先经这个过滤器：从 Header 取 `Authorization: Bearer xxx`，解析 Token，验证签名和过期时间，通过后放行给 Controller。

**③前端存储 — `request.js`**（`dormitory-web/src/utils/request.js`）
登录成功后 Token 存 sessionStorage（按角色分 key，如 `admin_token`、`student_token`）。请求拦截器自动在每次请求头里带 Token。响应拦截器捕获 401，就清空 Token 跳转登录页。

操作流程：用户登录 → 后端验证 → 生成 JWT → 前端存 → 每次请求带 → 过滤器验证 → 放行或拒绝。

## Q6：登录时怎么验证密码的？

核心代码在 `dormitory-admin/src/main/java/com/dormitory/service/impl/AuthServiceImpl.java`。

流程四步：
1. 用户输入用户名 + 密码，前端 POST 到 `/api/auth/login`
2. 后端根据用户名从数据库查出用户记录，里面有 BCrypt 加密后的密文
3. 调 `passwordEncoder.matches(输入的明文, 数据库的密文)` — BCrypt 会自动从密文中提取盐值，把明文加盐后做 1024 轮哈希，跟存储的密文比对
4. 匹配成功就生成 JWT 返回，失败就返回密码错误

关键点是 **BCrypt 是单向的，只能比对不能解密**。整个过程不需要、也没办法把密文"解密"成明文。

## Q7：在线报修功能怎么实现的？

这是一个完整的状态机流程。后端 Controller：`dormitory-admin/src/main/java/com/dormitory/controller/RepairController.java`

**四个状态**（定义在 `Constant.java`）：
- 0 = 待处理（学生刚提交）
- 1 = 已接单（宿管接了）
- 2 = 维修中
- 3 = 已完成

**流程**：
- 学生端：填表单 → 选报修类型（水电/门窗/网络等，类型由管理员在 `RepairType` 表里维护）→ 可上传最多 4 张图片 → 提交，status 设为 0
- 宿管端：看到本楼栋报修列表，紧急工单会置顶标红 → 接单（status → 1）→ 可转派给维修师傅 → 开始维修（status → 2） → 完成后标记完成（status → 3）
- 完成维修后，系统自动发消息通知学生去评价。评价功能在 `RepairCommentController.java`，学生打分满意/一般/不满意。

前端页面：
- 学生端：`dormitory-web/src/views/student/repair/index.vue`
- 宿管端：`dormitory-web/src/views/manager/repair/index.vue`

## Q8：换寝申请功能怎么设计的？

后端：`dormitory-admin/src/main/java/com/dormitory/controller/RoomChangeController.java`

这个功能的核心难点是**审批通过后涉及 4 张表联动更新**，需要保证数据一致：

1. 释放原床位：`bed` 表状态改为"空闲"，清除学生绑定
2. 原宿舍人数 -1：`room` 表的 currentCount
3. 占用新床位：新 `bed` 表状态改为"占用"，绑定学生
4. 新宿舍人数 +1
5. 更新学生表：`student` 表的 roomId 和 bedNumber
6. 申请状态改为"已通过"

状态定义（`Constant.java`）：0=待审批，1=已通过，2=已拒绝。

学生端页面：`dormitory-web/src/views/student/room-change/index.vue`
宿管审批页面：`dormitory-web/src/views/manager/room-change/index.vue`

数据权限：学生只能看自己的申请，宿管看本楼栋的，管理员看全校的。

## Q9：智能客服怎么实现的？

这是项目的创新点，对接了 DeepSeek 大模型。

后端：`dormitory-admin/src/main/java/com/dormitory/controller/ChatController.java`

两种模式：
- chatType=1，智能客服：学生发消息 → 后端调 DeepSeek API（`https://api.deepseek.com/v1/chat/completions`）→ 拿到 AI 回复 → 自动存入数据库 → 返回给学生
- chatType=2，人工客服：学生发消息 → 转给管理员在后台回复

数据库两张表：`chat_session`（会话）和 `chat_message`（消息），支持多轮对话。

AI 调用的代码在 ChatController 的 `getAIResponse()` 方法里，用 Java 11 的 HttpClient 发请求，设了 30 秒超时。如果 AI 不可用会返回提示让学生转人工。

前端页面：`dormitory-web/src/views/student/chat/index.vue`

## Q11：系统做了哪些性能优化？

主要有五点：

1. **HikariCP 连接池**：`application.yml` 里配了最大 50 个连接，HikariCP 是目前 Java 性能最高的连接池，Spring Boot 默认就用它。

2. **避免 N+1 查询**：比如学生列表，原来查完学生再循环查宿舍信息，改成了用 `LEFT JOIN` 一次查出所有关联数据。具体在学生相关接口里，用 MyBatis-Plus 的 `LambdaQueryWrapper` 拼条件，避免循环里重复查库。

3. **分页查询**：所有列表接口都用 MyBatis-Plus 的 `Page` 做分页，不一次查全表。前端用 Element Plus 的 `el-pagination` 组件配合。

4. **JWT 无状态**：服务端不存 Session，不占内存，扩容也方便，加服务器就行不用做 Session 同步。

5. **前端路由懒加载**：`dormitory-web/src/router/index.js` 里所有页面都是 `() => import(...)` 动态导入，首屏只加载当前页面，其他页面用到才加载。

## Q12：数据传输安全吗？存储和传输有什么区别？

存储和传输要分开看：

**存储**：密码是 BCrypt 加密存储的，数据库里看不到明文。其他业务数据（姓名、学号等）是按真实值存的，因为查询和展示需要。

**传输**：目前开发阶段是 HTTP 明文传输。部署到生产环境时需要配置 HTTPS（SSL/TLS 证书），这样请求体和响应体在网络上就是加密的。

简单说：密码存储加密了 ✅，但传输层加密需要部署 HTTPS 才算完整 ✅。

## Q13：权限控制是怎么实现的？不同角色看到的数据有什么区别？

系统用的是**数据层面的细粒度权限控制**，而不是简单的 URL 拦截。

`JwtAuthenticationFilter.java` 解析 Token 后，会把 userId 和 userType 放进请求上下文。Controller 里根据这两个值做数据过滤：

| 场景 | 学生 | 宿管 | 管理员 |
|---|---|---|---|
| 查询报修 | 只查自己的 repair | 查本楼栋的 | 查所有的 |
| 查询水电费 | 只查自己宿舍 | 查本楼栋 | 查所有宿舍 |
| 查询学生 | 只看自己信息 | 看本楼栋学生 | 看全部学生 |

举例：宿管调 `/api/repair/list`，Controller 里会先拿到当前宿管的 buildingId，然后 `LambdaQueryWrapper` 加条件 `eq(Repair::getBuildingId, buildingId)`，只返回本楼栋数据。

这样做的好处是不需要每个接口加 `@PreAuthorize` 注解，数据过滤逻辑灵活，适合业务场景。

## Q14：RESTful API 的 GET/POST/PUT/DELETE 有什么区别？

在本项目中遵循 RESTful 规范：

- **GET**：查询。幂等，多次调用结果一样。比如 `GET /api/student/list?pageNum=1&pageSize=10`
- **POST**：新增。非幂等，每次调用创建新记录。比如 `POST /api/student` 新增学生
- **PUT**：更新。幂等，多次更新同一数据结果不变。比如 `PUT /api/student` 编辑学生信息
- **DELETE**：删除。幂等，删除已删除的数据不会有副作用。比如 `DELETE /api/student/{id}`

具体代码在每个 Controller 里，比如 `StudentController.java` 里：
- `@GetMapping("/list")` 查列表
- `@PostMapping` 新增
- `@PutMapping("/update")` 更新
- `@DeleteMapping("/{id}")` 删除

## Q15：Excel 导入导出怎么实现的？

用的是 **Apache POI** 库，依赖在 `pom.xml` 里：`poi-ooxml 5.2.5`。

**导出**（以学生导出为例）：后端用 `XSSFWorkbook` 创建工作簿 → 建 Sheet → 写表头行 → 循环数据写行 → 设响应头 `Content-Disposition: attachment;filename=students.xlsx` → 浏览器自动下载。

**导入**：前端用 `el-upload` 组件上传 Excel → 后端接收 `MultipartFile` → `XSSFWorkbook` 读取 → 逐行解析 → 批量插入数据库。

具体代码在 `StatisticsController.java` 里有 export 和 import 方法，另外各业务 Controller（`StudentController`、`UtilityController` 等）也有各自的导入导出。

支持的模块：学生信息（导入+导出）、水电费（Excel 导入）、打卡记录（导出）、报修记录（导出）。

## Q16：Token 过期了怎么办？失效处理怎么做的？

**过期时间**：`application.yml` 里配置 `jwt.expiration: 604800000`，即 7 天。

**失效后的处理**全在前端 `request.js` 的响应拦截器里：

1. 后端在 `JwtAuthenticationFilter` 里发现 Token 过期或无效，返回 401
2. 前端的 axios 响应拦截器捕获 401 → `ElMessage.error("登录已过期，请重新登录")` → 清空 `sessionStorage` 里的 Token 和用户信息 → `router.push("/login")` 跳回登录页

这样用户体验是：在系统里操作着，突然 Token 过期了，点任何按钮都会被弹到登录页。

## 答辩技巧提醒

1. **不要说"代码已省略"** — 直接说文件名，哪怕不展示代码，老师知道你清楚位置
2. **不要主动暴露问题** — 比如别说"权限有漏洞""数据传输不安全"，这些都是扣分点
3. **回答简洁** — 老师一个问题一般 1-2 分钟答完，先说结论再说细节
4. **被追问细节时** — 直接说"这个功能在 XXController.java 里实现的，核心逻辑是……"
5. **不确定的问题** — 诚实说"这部分我开发时主要关注了 A 和 B，C 这块我后续会继续完善"
