# 智能宿舍管理系统 — 项目优化建议

> 基于完整代码审计 + 论文交叉核验，按优先级排序。**仅列出问题，不修改代码。**

---

## 一、🔴 高优先级（功能正确性 / 数据安全）

### 1.1 换寝审批缺少事务保护

**位置**：`dormitory-admin/.../controller/RoomChangeController.java` 的 `approve()` 方法

**问题**：审批通过后执行 6 步操作（释放原床位 → 原宿舍人数-1 → 占用新床位 → 新宿舍人数+1 → 更新学生住宿信息 → 更新申请状态），但**没有任何 `@Transactional` 注解**。中途任何一步失败，前面的操作不会被回滚，会导致床位状态、宿舍人数、学生信息三者不一致。

**建议**：在方法上添加 `@Transactional(rollbackFor = Exception.class)`，或将业务逻辑抽到 Service 层并加事务。

### 1.2 全局 0 个 Controller 使用了 @Transactional

**数据**：28 个 Controller 共 0 处 `@Transactional`

**问题**：所有涉及多表写操作的 Controller（换寝、退寝、报修状态变更、水电费录入+预警、文明宿舍计算+排名）都没有事务保护。在生产环境中，数据库连接中断或并发冲突会导致脏数据。

### 1.3 敏感信息硬编码在 application.yml

**位置**：`dormitory-admin/src/main/resources/application.yml`

**暴露的信息**：
- 数据库密码：`password: 123456`
- DeepSeek API Key：`sk-4a73a8cbe73c479b90b5605b615c5af0`
- JWT 密钥：`dormitory-system-secret-key-2026`

**建议**：用环境变量或 Spring Boot 的 `@Value` + 外部配置替换。至少答辩时不能说"硬编码"，要提一句"部署时移到环境变量"。

### 1.4 SecurityConfig 没有角色级 URL 保护

**位置**：`SecurityConfig.java` 第 84-88 行

**当前代码**：
```java
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/auth/**").permitAll()
    .anyRequest().authenticated()  // 只验证登录，不验证角色
)
```

**问题**：学生登录后可以访问 `/api/admin/*` 路径。权限控制在 Controller 里靠数据过滤实现，但接口层级没有拦截。论文 6.2.3 节说"返回 403"，与代码实际行为不符。

**建议**：加 `hasRole()` / `hasAuthority()` 做接口级权限，形成双保险。

## 二、🟡 中优先级（代码质量 / 性能）

### 2.1 没有 Service 层（除 AuthService 外）

**现状**：28 个 Controller，只有 `AuthService` + `AuthServiceImpl` 有独立的 Service。其他 27 个 Controller **直接在 Controller 里注入 Mapper 并写业务逻辑**。

**问题**：
- Controller 层承担了 Service 层的职责，违反了 MVC 分层原则
- 换寝审批的几十行业务逻辑全在 Controller 里，无法被其他模块复用
- 无法做单元测试（只能测整个 HTTP 请求）

**建议**：至少把换寝审批、报修状态流转、水电费计算+预警、文明宿舍评分这些复杂逻辑抽到独立 Service。

### 2.2 StudentController 第 479 行附近仍有 N+1 查询

**位置**：`StudentController.java` 约第 479 行

**问题**：
```java
List<Bed> allBeds = bedMapper.selectList(null);  // 全表扫描
// 循环里：
Room room = roomMapper.selectById(bed.getRoomId());        // N+1
Building building = buildingMapper.selectById(room.getBuildingId()); // N+1
```

list() 方法（第 188 行）已优化为批量查询，但同一 Controller 的其他方法还是老写法。同样的问题可能存在于 `BuildingController`、`RoomController` 等涉及关联查询的 Controller 中。

### 2.3 生产环境 SQL 日志未关闭

**位置**：`application.yml`

```yaml
mybatis:
  configuration:
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl  # 每条 SQL 都输出到控制台
```

**问题**：StdOutImpl 在生产环境下会严重影响性能，每次 SQL 执行都走一次 System.out.println。开发环境没问题，但部署前应该切换到 SLF4J 或关闭。

### 2.4 异常处理过于宽泛

**数据**：28 个 Controller 中约 20 处 `catch (Exception e)`，且大部分没有具体处理逻辑（只打印日志或直接返回）

**典型问题**：
- `catch (Exception e)` 捕获了所有异常，包括 NullPointerException 这种代码 Bug
- 错误信息可能暴露内部细节给前端
- 全局异常处理器 `GlobalExceptionHandler.java` 只覆盖了部分场景

### 2.5 application.yml 中连接池未针对并发优化

**当前配置**：
- `maximum-pool-size: 50`
- `minimum-idle: 10`
- `connection-timeout: 30000`

**问题**：
- 50 个连接对于 500+ 并发不足（论文测试已验证，99% 分位达到 2858ms）
- 但日常使用 50 足够
- 建议根据实际部署环境动态调整，论文/答辩时可说"当前开发配置，生产环境会调大"

## 三、🟢 低优先级（改善体验 / 架构演进）

### 3.1 前端 API 层严重不足

**现状**：`dormitory-web/src/api/` 只有 2 个文件（`auth.js`、`admin.js`，共 60 行），而所有 `.vue` 文件中有 **325 处** 直接写 `request.post/get/put/delete`。

**问题**：
- API 路径散落各处，改一个路径需要全局搜索
- 相同接口被多个组件重复调用时，参数和响应处理不一致
- 没有统一的接口类型定义

**建议**：至少把报修、学生、宿舍、水电费等核心模块的 API 抽到独立文件（`api/repair.js`、`api/student.js` 等）。

### 3.2 BCrypt 验证成为登录瓶颈

**位置**：`AuthServiceImpl.java` — `passwordEncoder.matches()`

**分析**：BCrypt cost=10 意味着每次登录要进行 1024 轮哈希计算，耗时 100-200ms。1000 并发登录时，50 个连接 + BCrypt 慢哈希形成双瓶颈。

**建议**：cost 降到 8 可以节省约一半时间，或在登录前加验证码/限流来防护暴力破解（这样 BCrypt 的"慢"就不再是安全必需）。

### 3.3 消息通知无实时推送

**现状**：消息通知靠前端轮询刷新，没有 WebSocket。

**影响**：学生提交报修后，宿管不会立即收到提醒；学生需要通过刷新页面来查看回复。

**建议**：引入 Spring WebSocket + STOMP，或在论文展望中提及。

### 3.4 文件上传无类型校验

**位置**：`UploadController.java`

**问题**：代码中没有看到对上传文件的 MIME 类型校验。用户可能上传非图片文件（如 exe、脚本）伪装成图片。

**建议**：加文件头校验（Magic Number）或限制允许的 MIME 类型。

### 3.5 没有 API 文档

**现状**：项目中没有任何 Swagger/OpenAPI 注解。

**建议**：引入 SpringDoc OpenAPI（`springdoc-openapi-starter-webmvc-ui`），在 Controller 上加注解即可自动生成接口文档页面（`/swagger-ui.html`）。

### 3.6 没有缓存层

**分析**：
- 宿舍楼列表、报修类型列表等几乎不变的数据，每次请求都查数据库
- 文明宿舍排名每月才更新一次，每次查看都实时计算

**建议**：引入 Spring Cache（`@Cacheable`）+ Redis 或 Caffeine。论文展望中已提及。

### 3.7 未使用数据校验注解

**现状**：28 个 Controller 中极少使用 `@Valid` / `@Validated` 注解。

**问题**：参数校验靠手动 `if` 判断，代码重复且容易遗漏。

**建议**：在 DTO 字段上加 `@NotBlank`、`@NotNull`、`@Size` 等注解，Controller 参数上加 `@Valid`。
