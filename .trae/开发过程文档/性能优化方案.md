# 智能宿舍管理系统性能优化方案

## 一、前言

通过对系统架构和代码的分析，当前系统采用传统的单体架构模式，未使用Redis缓存、异步处理等优化手段，在高并发场景下可能出现性能瓶颈。本文档针对500人并发访问的性能目标，提出系统性的优化方案。

## 二、当前系统性能瓶颈分析

### 2.1 数据库连接池配置不足

系统当前使用HikariCP连接池，默认配置最大连接数仅为10。在500并发场景下，连接池很快就会耗尽，导致请求等待数据库连接，后续请求堆积，系统响应变慢。

### 2.2 缺乏缓存机制

系统所有数据查询均直接访问数据库，包括学生信息、宿舍信息、楼栋信息等热点数据。这些数据查询频率高但变化频率低，非常适合使用缓存来减轻数据库压力。当前系统缺乏缓存机制，每次请求都需要查询数据库，数据库I/O成为主要瓶颈。

### 2.3 智能客服AI调用为同步阻塞

系统集成了DeepSeek AI接口实现智能客服功能，但AI调用采用同步阻塞模式。当AI接口响应较慢时，会占用服务器线程资源，导致线程池耗尽，影响其他用户的正常使用。

### 2.4 部分查询未分页

代码中存在 selectList(null) 全量查询的情况，当数据库记录增多时，查询性能会显著下降，同时占用大量内存资源。

### 2.5 缺乏异步处理机制

消息通知、批量数据处理等操作均为同步执行，这些操作不要求实时性，但会占用用户请求的响应时间。

## 三、优化方案

### 3.1 数据库连接池优化

通过修改application.yml配置文件，扩大HikariCP连接池容量，使其能够支撑更高的并发访问。

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 50        # 最大连接数调整为50
      minimum-idle: 10            # 最小空闲连接数
      connection-timeout: 30000   # 连接超时时间30秒
      idle-timeout: 600000        # 空闲超时时间10分钟
      max-lifetime: 1800000       # 最大生命周期30分钟
```

此配置可使系统同时处理50个数据库查询，结合业务逻辑执行时间，理论上可支撑100-200的并发访问。

### 3.2 添加Redis缓存

引入Redis作为缓存层，对查询频率高、变化频率低的数据进行缓存。建议缓存以下数据：

- 学生基本信息（学号、姓名、班级等）
- 宿舍信息（楼栋、房间、床位）
- 楼栋信息
- 报修类型配置
- 系统配置参数

缓存实现示例：当查询学生信息时，先从Redis缓存中查找，命中则直接返回，未命中则查询数据库并写入缓存。同时设置缓存过期时间（如1小时），确保数据及时更新。

### 3.3 智能客服异步改造

将DeepSeek AI调用改为异步执行，用户发送消息后立即返回成功，AI调用在后台异步处理，处理完成后通过WebSocket或轮询机制将结果推送给用户。

```java
// 异步调用AI
@Async
public CompletableFuture<String> getAIResponseAsync(String question) {
    String response = getAIResponse(question);
    return CompletableFuture.completedFuture(response);
}
```

### 3.4 查询分页优化

所有列表查询接口强制添加分页参数，前端默认分页大小为10-20条，避免全量查询。

```java
@GetMapping("/list")
public Result<Page<Student>> list(
        @RequestParam(defaultValue = "1") Integer pageNum,
        @RequestParam(defaultValue = "10") Integer pageSize) {
    // 限制最大分页大小，防止一次查询过多数据
    if (pageSize > 50) pageSize = 50;
    Page<Student> page = new Page<>(pageNum, pageSize);
    // ... 查询逻辑
}
```

### 3.5 异步消息通知

将消息通知、批量操作等非实时性任务改为异步执行，通过Spring的@Async注解或消息队列实现。

```java
@Async
public void sendNotificationAsync(Long userId, String title, String content) {
    // 发送通知的逻辑
}
```

### 3.6 数据库索引优化

分析系统SQL查询日志，识别高频查询字段，添加适当的索引。例如：

- student表：student_number、name、building_id、room_id
- repair表：student_id、status、create_time
- check_in表：student_id、check_date

## 四、优化效果预估

| 优化措施 | 预期提升效果 |
|----------|--------------|
| 连接池优化 | 并发处理能力提升3-5倍 |
| Redis缓存 | 查询响应时间降低50%-80% |
| 异步AI调用 | 智能客服响应能力提升10倍 |
| 查询分页 | 列表查询内存占用降低90% |
| 异步消息 | 主流程响应时间缩短30% |

## 五、优化优先级建议

考虑到开发成本和时间，建议按以下优先级实施优化：

**第一阶段（简单优化，优先级高）**

- 数据库连接池配置调整
- 查询分页限制
- 数据库索引添加

**第二阶段（效果明显，优先级中）**

- Redis缓存集成
- 异步消息机制

**第三阶段（深度优化，优先级低）**

- 智能客服异步改造
- 分布式架构改造（如需要）

## 六、总结

通过以上优化措施，预期系统可以满足500人并发访问的性能要求。建议先实施第一阶段的优化，然后进行性能测试，根据测试结果决定是否进行后续优化。性能优化是一个迭代过程，需要结合实际测试数据不断调整和完善。
