## 一、开发过程类（几乎必问）

### Q：开发这个项目花了多久？
**答**：从选题到完成大约三个月。第一阶段搭框架和数据库设计，第二阶段写核心业务（登录、报修、宿舍管理），第三阶段加扩展功能（AI客服、水电预警、文明宿舍），最后测试和写论文。

### Q：你是怎么用 TRAE 开发的？和普通 IDE 有什么区别？
**答**：TRAE 是一个 AI 辅助编程工具，我主要用它来生成基础代码框架、Controller 和 Mapper 的模板代码，然后自己调整业务逻辑。前端页面的表单和表格也是用它快速生成的，我再根据需求改细节。它节省了很多重复代码的编写时间。

### Q：你提到了 TRAE，哪些代码是 AI 写的，哪些是你自己写的？
**答**：AI 帮我生成了基础的 CRUD 模板和前端页面框架。核心业务逻辑是我自己设计和实现的，比如报修状态流转、换寝多表联动更新、N+1 查询优化这些。数据库 29 张表的设计也是我自己做的，因为需要理解业务关系。

### Q：开发中遇到的最大困难是什么？
**答**：一个是换寝审批的多表联动更新——审批通过后要同时改 bed、room、student 三张表，必须保证数据一致。我把它写在一个方法里，靠数据库事务保证原子性。另一个是学生列表的 N+1 查询，原来页面要加载 2 秒，后来改成批量查询降到了 50ms。

## 二、数据库深入类

### Q：29 张表之间怎么关联的？外键在哪？
**答**：用 ID 做逻辑关联，没有使用数据库物理外键（物理外键在高并发下影响性能，实际项目里通常不用）。比如 student 表里存 building_id、room_id，repair 表里存 student_id、room_id、type_id。关联关系在代码层用 MyBatis-Plus 的查询来维护。

### Q：哪些字段建了索引？
**答**：student 表的 student_number（学号唯一查询）、building/room/bed 表的关联 ID、repair 表的 student_id 和 status（按学生查报修记录、按状态筛选）。SQL 脚本在项目根目录 dormitory_system.sql。

### Q：为什么用 MySQL 而不是其他数据库？
**答**：MySQL 免费开源，中小型应用性能足够。我只需要关系型存储，不需要 MongoDB 这样的文档数据库。PostgreSQL 功能更强但我对 MySQL 更熟悉。

## 三、安全类追问

### Q：SQL 注入怎么防的？
**答**：MyBatis-Plus 的 LambdaQueryWrapper 用 Lambda 表达式拼查询条件，参数会以预编译方式传给 SQL，不是字符串拼接，所以天然防 SQL 注入。

### Q：XSS 攻击怎么处理的？
**答**：前端 Vue 3 默认对 `{{ }}` 插值做 HTML 转义，用户输入 `<script>alert(1)</script>` 会被显示成文本而不是执行。后端存储时不做额外处理，因为前端展示时已经转义了。

### Q：如果两个人同时选同一个床位换寝怎么办？
**答**：换寝在 RoomChangeController 的 approve 方法里，审批通过时会先检查床位是否还空闲（status == 0），如果有人抢先占了，后续的审批会返回"目标床位不可用"。这是数据库层面的并发安全——UPDATE 操作是原子的。

## 四、前端类追问

### Q：Vue Router 路由守卫怎么做的？
**答**：路由配置在 dormitory-web/src/router/index.js。每个角色有独立的路由前缀（/student、/manager、/admin），进入前检查 sessionStorage 里有没有对应角色的 token，没有就跳登录页。

### Q：Element Plus 用了哪些组件？
**答**：el-table（数据表格）、el-form（表单）、el-dialog（弹窗）、el-pagination（分页）、el-upload（文件上传）、el-select/el-date-picker（筛选）、el-tag（状态标签）、el-descriptions（详情展示）。还有 ECharts 做柱状图和扇形图。

### Q：布局怎么做的？三个角色的页面怎么切换？
**答**：每个角色有自己的布局组件，比如 student/layout/index.vue 包含侧边栏导航和顶部栏，内容区用 `<router-view>` 切换。登录时根据 userType 跳不同路由前缀，拿到不同的菜单。

## 五、部署与运维

### Q：系统怎么部署到服务器上？
**答**：后端 Spring Boot 用 Maven 打 jar 包，`java -jar` 启动。前端 `npm run build` 生成静态文件，放 Nginx 下。Nginx 配反向代理，`/api` 转发给后端 8080。数据库提前执行 dormitory_system.sql 初始化表结构和基础数据。

### Q：系统能支撑多少用户同时使用？
**答**：当前开发环境测了 1000 并发的登录和查询，核心接口能支撑日常使用。如果真要上线，需要加 Redis 缓存、数据库读写分离、连接池调大、前后端部署到独立服务器。

## 六、论文相关追问

### Q：国内外研究现状你是怎么写的？参考了哪些文献？
**答**：国内研究偏重功能全面、流程完整，但同质化高；国外研究架构规范、技术聚焦，但不符合国内宿舍管理制度。我的系统取了两边的长处——功能全面 + 架构规范，并加了 AI 客服和水电预警这些现有系统没有的功能。参考文献 20 多篇，近三年的为主。

### Q：论文里哪些是你自己的贡献？
**答**：一是把 AI 大模型集成到宿舍管理系统做 24 小时智能客服；二是水电费按宿舍类型区别定价 + 超限自动预警；三是 29 张表的完整数据库设计。这些是我独立完成的。

### Q：你觉得自己的系统有什么不足？
**答**：第一，目前只有 PC Web 端，没有移动端小程序，学生用手机访问不方便。第二，智能客服的回答质量依赖 DeepSeek API，网络不好的时候会不可用。第三，权限控制在接口层还不够严格，后续可以加 `@PreAuthorize` 注解做接口级拦截。第四，数据统计还比较基础，可以加更多维度的分析。

## 七、突发/刁钻问题

### Q：你说用了 Pinia，论文里为什么写 Vuex？
**答**：论文初稿写的时候还在用 Vuex，后来发现 Vue 3 官方推荐 Pinia，实际开发中改了过来。Pinia 本质上是 Vuex 的升级版，API 更简洁。

### Q：localStorage 和 sessionStorage 到底用哪个？
**答**：实际代码用的是 sessionStorage，因为更安全——关浏览器 Token 就没了，防止别人用你的电脑继续登录。论文里描述有误，我在答辩准备时注意到了这个差异。

### Q：你说 BCrypt 安全，那如果数据库被盗了怎么办？
**答**：BCrypt 是单向哈希，即使数据库完全泄露，黑客也还原不了明文密码。他能看到的是 `$2a$10$...` 这种密文，暴力破解一个密码要花几百年。不过用户的其他信息（姓名、学号、电话）是明文存储的，这是后续需要加强的方向——可以对敏感字段做数据库层面加密。

### Q：如果有 10000 个学生同时打卡会怎样？
**答**：目前开发环境肯定扛不住，连接池才 50。如果真要应对这个量级，需要：连接池调到 200+、加 Redis 缓存、打卡接口做异步处理（消息队列削峰）、数据库做读写分离。我在论文第 7 章结论里也写了"后续可以引入大数据技术"。
