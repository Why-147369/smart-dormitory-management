# 第一部分：基于论文内容的常见提问

## Q1：为什么选这个课题？有什么实际意义？

高校宿舍管理长期靠人工——报修要跑腿、水电费要上门抄表、查信息要去管理处。这套系统把宿舍管理全流程线上化，减少人工干预。论文第1章写了：目前高校招生规模扩大，传统方式"信息不及时，数据统计困难，报修效率低"。系统让学生在线办业务、宿管高效管楼栋、管理员有数据做决策。

## Q2：为什么选 Spring Boot + Vue 这套技术栈？

论文第2章有详细说明。Spring Boot 省去了传统 Spring 的繁琐配置，启动器和自动配置能快速集成 MyBatis-Plus、Spring Security（色酷睿提）。Vue 3 组件化开发效率高， Element Plus 是一个 UI 组件库，提供现成的按钮、表格、表单、弹窗等界面组件，你直接拿来用，不用自己写 CSS。前后端分离，各自独立部署和维护。MySQL 免费开源，对学生项目够用。

如果老师问"B/S和C/S有什么区别"：B/S 用浏览器访问不用装软件，C/S 要装客户端（如微信、QQ）。本系统选 B/S 是因为学生宿管用浏览器打开就能用。

## T1：密码加密怎么做的？用什么算法？为什么选它？

用的是 BCrypt 加密算法，Spring Security 自带的 BCryptPasswordEncoder。

为什么选 BCrypt 而不是 MD5 或 SHA256：

① MD5/SHA256 是"快哈希"，几微秒就能算完，黑客用 GPU 一秒能试几十亿次，暴力破解太快

② BCrypt 是"慢哈希"，专门为密码存储设计的，默认计算 1024 轮，每次加密要 100-200 毫秒。对正常用户登录几乎无感，对黑客暴力破解是天堑

③ BCrypt 每次加密自动生成随机"盐值"混入密码，两个用户设相同密码，数据库里密文也不同。黑客没法用彩虹表批量比对

简单理解：MD5 像一把普通锁，钥匙对了秒开。BCrypt 像一把需要 100 道工序才能转动的锁——主人开锁等 0.1 秒无所谓，小偷要试 100 万个密码就得等到天荒地老。

代码位置：SecurityConfig.java 定义 BCryptPasswordEncoder Bean → 新增用户时调 .encode("密码") 加密存库 → 登录时调 .matches(输入密码, 库中密文) 比对（不解密，只比对）。

## T2：JWT Token 认证流程是怎样的？Token 过期怎么处理？

**认证流程**：JwtUtil.java 生成和解析Token → JwtAuthenticationFilter.java 拦截每个请求验证Token → AuthServiceImpl.java 登录时调用生成。前端在 request.js 里统一带 Token（放 Authorization 头里），用 sessionStorage 存储，关浏览器即失效。

**Token 过期处理**（分两步）：

① 后端 `JwtAuthenticationFilter.java` 第 53 行：每个请求到达时调用 `jwtUtil.validateToken(token)`，如果过期或无效，不设置认证信息到 SecurityContext。Spring Security 检测到"未认证"后自动返回 **401**。

② 前端 `request.js` 第 49-65 行：axios 响应拦截器捕获 401 → 弹窗提示"登录已过期，请重新登录" → 清除 sessionStorage 中的 token、userInfo、userType → `window.location.href = '/login'` 强制跳转登录页。

用户表现：在系统中操作时 Token 突然过期，点击任何按钮都会被弹回登录页，重新登录即可继续使用。

| 文件 | 路径 | 作用 |
|------|------|------|
| JwtUtil.java | dormitory-admin/.../utils/ | generateToken() 生成，parseToken() 解析，validateToken() 验证 |
| JwtAuthenticationFilter.java | dormitory-admin/.../config/ | 第 53 行：拦截请求，验证失败不设认证 → 返回 401 |
| AuthServiceImpl.java | dormitory-admin/.../service/impl/ | 登录成功调用 JwtUtil 生成 Token |
| application.yml | dormitory-admin/src/main/resources/ | jwt.expiration: 604800000（7天） |
| request.js | dormitory-web/src/utils/ | 第 49-65 行：捕获 401 → 清 sessionStorage → 跳 /login |

## T4：换寝功能怎么保证数据一致？

RoomChangeController.java 里 approve 方法，审批通过后在一个事务里完成6步：①释放原床位(bed表状态→空闲) ②原宿舍人数-1 ③占用新床位 ④新宿舍人数+1 ⑤更新student表的roomId和bedNumber ⑥申请状态→已通过。所有操作在一个方法里，数据库事务保证原子性，要么全成功要么全回滚。

## T5：AI 智能客服怎么接的？调了什么 API？业务逻辑是什么？

**API 调用**：ChatController.java 里 getAIResponse() 方法，用 Java 11 的 HttpClient 发送 POST 请求到 https://api.deepseek.com/v1/chat/completions，带上 API Key（配在 application.yml 的 deepseek.api-key）。设 30 秒超时，失败了返回"AI 服务暂时不可用"。

**业务逻辑**（ChatController.java）：

① 学生点击智能客服 → 创建会话（chat_session 表），chatType=1 表示 AI 客服

② 学生发送消息 → 存入 chat_message 表（senderType=1 表示学生）

③ 系统判断 chatType：如果是 AI 客服 → 调 DeepSeek API → 拿到回复 → 存入 chat_message（senderType=2 表示 AI）

④ 如果学生选择人工客服（chatType=2）→ 消息推给管理员端 → 管理员回复 → senderType=3 表示管理员

⑤ 会话结束 → chat_session.status 从 0（进行中）改为 1（已结束）

⑥ 学生可查看历史客服记录，按会话分组

数据库两张表：chat_session（会话）+ chat_message（消息），支持多轮对话。chat_type=1=AI客服，chat_type=2=人工客服。

## T6：水电费怎么算的？超限预警怎么做？

UtilityThresholdController.java 里管理员配置不同宿舍类型（4/6人间）的单价和限额。UtilityController.java 里宿管录入水电用量时，系统自动读对应单价计算费用。checkAndCreateWarning() 方法检查是否超限，超了就创建预警记录并给该宿舍所有学生推送消息通知。学生端模拟支付：选微信/支付宝 → 弹二维码 → 15秒后自动标记已支付。

## T7：权限控制怎么做的？学生能看到宿管的数据吗？

数据层面的细粒度控制。JwtAuthenticationFilter 验证 Token 后把 userId 和 userType 放入上下文。Controller 里根据 userType 过滤数据：比如宿管调 GET /api/repair/list，只返回本楼栋的报修单（LambdaQueryWrapper 加 buildingId 条件）。学生只能看自己的，宿管看本楼栋，管理员看全部。

## T8：Excel 导入导出用的什么库？怎么做的？

## T9：学生列表查询做过什么性能优化？

这是项目中最有价值的一个技术优化，解决了经典的 N+1 查询问题。

优化前的问题：学生列表接口查询一次分页学生（1次SQL），然后循环为每个学生查床位，再为每个床位查房间、查楼栋。总共 1501 次数据库查询，页面加载 2 秒。

优化方案：在 StudentController.java 的 list() 方法（第 188-236 行），改为批量查询 + 内存 Map 关联——

① 只查当前页学生的床位（用 IN 条件，1次SQL）

② 批量查所有相关房间（selectBatchIds，1次SQL）

③ 批量查所有相关楼栋（selectBatchIds，1次SQL）

④ 在内存里用 Map\<Long, Room> 和 Map\<Long, Building> 做关联组装

效果：总查询从 1501 次降到 4 次，页面加载从 2 秒降到约 50ms。

优化文档：项目根目录/学生列表查询性能优化方案.md

核心代码：dormitory-admin/src/main/java/com/dormitory/controller/StudentController.java

如果老师追问"整个系统都优化了吗"：核心 list 方法已优化，部分辅助方法后续可以继续优化。比如同一个 Controller 里第 479 行附近还有全表扫描床位的方法，是下一步优化的目标。

## T11：MyBatis-Plus 和普通 MyBatis 有什么区别？

MyBatis 需要手写 SQL 和 XML 映射文件。MyBatis-Plus 增强了它：单表 CRUD 不用写 SQL（BaseMapper 自带 selectList、insert、updateById），LambdaQueryWrapper 拼条件避免字段名写错（如 lambdaQueryWrapper.eq(Student::getName, "张三")），内置分页插件（new Page<>(pageNum, pageSize)）。复杂联表查询才需要手写 SQL。

## T12：Spring Security 在你项目里起了什么作用？

SecurityConfig.java：① 放行 /api/auth/\*\*（登录接口不拦截）② 其他接口必须认证。JwtAuthenticationFilter.java：每个请求到达后先解析 Token → 验证签名和有效期 → 把用户信息放入 SecurityContext → 放行。BCryptPasswordEncoder 的 Bean 也在这定义。

## T13：跨域问题怎么解决的？

后端 WebConfig.java 配了 CORS 跨域：允许前端 localhost:5173 的请求，允许带 Authorization 请求头。开发时 Vite 也配了 proxy 代理：/api 前缀的请求转给 localhost:8080。

## T14：打卡管理的业务逻辑是什么？

**文件**：CheckInController.java（`/api/checkin`）

**学生端**：

① 打卡（/record）：学生点击打卡 → 查今日是否已打卡 → 已打卡则提示"今日已打卡" → 未打卡则插入记录，自动判断是否超过 23:00 设置 isLate

② 补卡申请（/apply）：学生错过打卡 → 提交补卡申请，填写原因和日期 → status 设为待审批 → 推送给宿管

③ 查看打卡状态（/status）：查今日打卡记录，返回是否已打卡、打卡时间、是否迟到

④ 查看打卡历史（/history）：分页查询个人所有打卡记录，按日期倒序

**宿管端**：

⑤ 审批补卡（/apply/approve/{id}）：先检查该学生当天是否已有打卡记录 → 没有则自动补录一条（时间设为 22:30，标记为补卡，isLate=1）→ 更新申请状态为已通过

⑥ 拒绝补卡（/apply/reject/{id}）：设置申请状态为已驳回，记录驳回原因

⑦ 打卡统计（/list）：按楼栋和日期筛选打卡记录，批量查询学生信息 + 宿舍信息组装返回（用了 selectBatchIds 优化，非 N+1）

| 状态 | 含义 |
|------|------|
| 0 | 补卡记录 |
| 1 | 正常打卡 |
| isLate=0 | 未迟到（23:00 前） |
| isLate=1 | 迟到（23:00 后） |

# 第四部分：答辩应急技巧

## 如果不确定答案

"老师，这部分我开发时主要关注了 A 和 B，您问的 C 我后续会继续研究完善。"——诚实但表明自己有思考。

## 如果被追问代码细节

直接说文件名："这个功能在 XXController.java 里实现的，我可以打开给您看。"——知道代码在哪比背代码重要。

## 如果被质疑技术选型

"选 Spring Boot 是因为它自动配置省时间，Vue 3 是因为组件化开发效率高。"——不要辩解，客观说理由。

## 如果老师指出论文错误

"谢谢老师指出，论文里这部分写得不够准确，实际实现中是……"—大方承认，给出正确信息。特别是 Vuex vs Pinia、localStorage vs sessionStorage 这两个已知差异。

## 如果演示时系统挂了

"可能是环境问题，我之前测试时一切正常。我可以先用代码给老师看这个功能的实现。"——提前准备好 IDE 里的代码，随时可以切过去展示。
