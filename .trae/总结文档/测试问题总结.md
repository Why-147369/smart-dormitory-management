# 测试数据错误原因分析

> 基于你的 6 个 JMeter .jmx 文件逐行分析

***

## 一、登录并发测试（线程组.jmx）— 数据不对的主要原因

**你的 JMX 配置**：

- 1000 个线程，ramp-up 只有 **10 秒**（每秒启动 100 个线程）
- CSV 文件：300名学生登录测试文件.csv
- CSV 配置：`recycle=true`（用完从头循环）、`shareMode=all`（所有线程共享）

**为什么数据不对**：

| 问题                  | 说明                                                                                                                |
| ------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **每秒100线程太猛**       | 10秒内塞 1000 个请求，BCrypt 每次验证就要 100-200ms，DB 连接池才 50 个。前 50 个请求把连接池占满，后面 950 个在排队                                    |
| **只有 300 个账号循环用**   | 1000 个线程抢 300 个账号，recycle=true 意味着第 301 个线程开始重用账号。同一个账号可能同时有 3-4 个线程在登录                                           |
| **BCrypt 105ms 太快** | 正常 BCrypt 验证一次要 100-200ms，加上查数据库 + 生成 JWT，单次登录至少 150-250ms。1000 并发下平均 105ms 几乎不可能——除非很多请求根本没走到 BCrypt 就失败了，拉低了平均值 |

**更合理的做法**：

- 准备 1000 个不同的测试账号（至少 500 个）
- ramp-up 设 60 秒以上，让请求缓慢叠加
- 或者用阶梯加压模式：100 → 300 → 500 → 1000，每步持续 2 分钟

***

## 三、数据提交测试（数据提交性能测试.jmx）— 归因 BCrypt 不完全对

**你的 JMX 配置**：

- 1000 线程，ramp-up 20 秒
- 所有线程用同一个 admin 登录 → 拿 token → POST `/api/student` 添加学生
- 每次添加都随机生成学号、姓名，密码固定 123456

**为什么归因不完全对**：

1. BCrypt.encode("123456") 确实每次消耗 \~150ms，但 1.36 秒里 BCrypt 只占约 11%
2. 剩余 1.2 秒大部分是：1000 个 INSERT 抢 50 个 DB 连接 + 唯一索引写入（学号有唯一约束）+ MySQL 锁竞争
3. 最大值 3584ms → 最小值 98ms，差距 36 倍，说明连接池排队极不均匀

**论文应该写的**："耗时主要来自 BCrypt 加密（约 150ms）和数据库并发写入竞争，连接池上限 50 导致大量请求排队"——而不是只提 BCrypt。

## 四、权限测试（权限测试.jmx）— 可能测的是不存在的接口

**你的 JMX 配置**：

- 学生登录 → 访问 `GET /api/admin/list`
- 宿管登录 → 访问 `GET /api/admin/user/list`
- 管理员登录 → 访问 `PUT /api/checkin/apply/approve/16`

**问题**：

1. **`/api/admin/list`** **和** **`/api/admin/user/list`** **是不同的路径**，`SecurityConfig.java` 里没有任何角色拦截，只有 `.anyRequest().authenticated()`。也就是说只要登录了，两个路径都能访问（不会返回 403）
2. 你的测试截图显示返回了 403，但代码里找不到对应拦截逻辑。可能的情况：
   - 测试时 AdminController 里恰好没有 `/list` 这个接口映射，返回了 404 被你当成 403
   - 或者测试时的代码和现在的代码不一样
   - 值得你自己开 JMeter 重新跑一遍确认

***

## 五、总结：你的三个测试数据为什么不合理

| 测试         | 论文数据     | 实际不可能的原因                                |
| ---------- | -------- | --------------------------------------- |
| 登录1000并发   | 平均 105ms | BCrypt 单次就要 100-200ms，1000并发105ms违背物理规律 |
| 查询500并发    | 平均 12ms  | 连接池50，450个排队，排队时间就超过12ms                |
| 添加学生1000并发 | 平均 1.36s | 数值本身合理，但论文把原因全归于BCrypt不准确，DB写入竞争才是大头    |

**根本原因**：JMeter 聚合报告的"平均值"把极端值平滑掉了。你的最大/最小值差距几十倍（如 98ms-3584ms），说明系统在处理队列时极不均匀。平均值 1.36s 看起来还行，但 99% 分位是 2858ms——100 个人里就有 1 个人等了快 3 秒。

**论文应该用"中位数"和"95%分位"来评价性能，而不是平均值。**
